## 一、产品定位

### D001 ✅ 项目名称：LexTrail
- 英文名 **LexTrail**，项目负责人认为读起来顺口。
- 已知同名情况（2026-10 调查）：
  - 拉美软件公司 Rubika 有一款同名的律所管理软件（不同市场、不同用途）。
  - PyPI 和 crates.io 上已有名为 `lextrail` 的开源库（大模型输出约束工具），**因此本项目发布的包不能使用 `lextrail` 作为包名**，需加前缀或后缀（如 `lextrail-core`）。
- 正式发布前须在中国商标网（第 9 类、第 42 类）、WIPO 全球品牌数据库中确认。
- 中文名：**词迹**（与英文名的 Trail，即"足迹"含义对应）。

### D002 ✅ 认真公开发布，面向他人使用
- 项目以开源方式公开发布，要能被其他人搜到和使用。
- 所有设计都要按"给陌生用户使用"的标准考虑：配置界面、安装包、自动更新、帮助文档、隐私说明。

### D003 ✅ 平台：先做 Windows，架构上为 macOS 预留
- 第一版只支持 Windows。
- 与平台相关的代码（取词、OCR、窗口管理等）必须通过统一接口隔离，以后增加 macOS 时上层代码不需要修改。

### D004 ✅ 常驻后台，低资源占用是硬性要求
- 软件需要长期常驻后台，资源占用必须严格控制。
- 具体性能目标见 `ARCHITECTURE.md` 中的"性能预算"。

## 二、技术栈与架构

### D005 ✅ 应用框架：Tauri 2 + Rust + Vue 3 + TypeScript
- **Tauri 2**：跨平台、安装包小、常驻内存远低于 Electron。
- **Rust**：负责取词、系统调用、数据库、网络请求、同步等全部核心逻辑。
- **Vue 3 + TypeScript + Vite**：负责界面。选择 Vue 的理由：上手难度低，本项目界面不复杂（悬浮窗、生词本、复习、设置）。
- 数据库：**SQLite**。

### D006 ✅ 核心逻辑放在独立的 Rust 模块中，界面层保持很薄
- 所有业务逻辑都放在独立的 Rust crate 中，界面只负责显示。
- 理由：
  1. 悬浮窗如需从 WebView 换成原生界面（见 D008），只需替换界面层。
  2. 核心模块可以被桌面端、服务端、手机端 PWA（编译为 WebAssembly）共用。

### D007 ✅ 架构核心原则："统一接口 + 可替换适配器"
- 同步传输、AI 服务商、取词平台、未来的官方服务，全部采用"定义统一接口，各实现作为可替换适配器"的方式。
- 新增一种同步方式、一个 AI 服务商或一个平台时，不应修改上层代码。

### D008 ✅ 悬浮窗采用路线 A（Tauri / WebView），不达标时切换到路线 B
- **路线 A**：悬浮窗和主窗口都使用 Tauri WebView。
- **路线 B（后备方案）**：悬浮窗改用 Slint 等轻量的 Rust 原生界面库，主窗口仍用 WebView。
- 先按路线 A 开发；在 M0 阶段做性能原型，按 `ARCHITECTURE.md` 中的性能预算实测。不达标则切换到路线 B。
- 已否决：每个平台各写一套原生程序（工作量翻倍，不适合个人开发的开源项目）；Electron（常驻内存过高）。

### D009 ⏳ 悬浮窗生命周期：默认一直保持挂起，不按时间销毁
- 三种状态：显示中 → 隐藏（几秒）→ 挂起（一直保持）。
- 挂起使用 WebView2 的 `TrySuspend` / `Resume`（不与 `MemoryUsageTargetLevel` 混用，二者只能选一组）。
- **默认不销毁**。只有在以下情况才销毁窗口：
  1. 收到系统低内存通知；
  2. 用户在设置中选择了"内存优先"模式（用完即销毁）。
- 设置项：**响应优先**（默认，一直挂起）/ **内存优先**（用完即销毁）。
- 理由：最初设计的"空闲 15–30 分钟后销毁"会导致零散查词的用户几乎每次都冷启动，使生命周期管理失去意义（由项目负责人指出）。
- 待验证：挂起状态的内存占用；**挂起 2 小时后**的恢复速度。若不达标，按 D008 切换到路线 B。
- 已于 M0 实测验证，结果见 D036。

### D010 ✅ 悬浮窗只有一个窗口，复用且不重新加载
- 全程只保留一个悬浮窗。每次查词通过事件推送新数据，页面原地更新。
- 悬浮窗与主窗口共用同一个 WebView2 环境。
- 悬浮窗是**单独打包的轻量页面**（Vite 多页面模式），不引入 UI 组件库、路由、状态管理库。
- 窗口直接显示，不加淡入动画；数据未就绪时显示骨架屏。

## 三、取词与触发方式

### D011 ✅ 取词顺序：UI Automation → 剪贴板兜底 → OCR
1. **UI Automation**：读取选中文本，尽量同时读取所在句子作为上下文，不污染剪贴板。
2. **剪贴板兜底**：模拟 Ctrl+C。必须做到：等待用户松开快捷键修饰键后再发送；用剪贴板序列号判断内容是否真的更新；读取后恢复原剪贴板内容；在终端中改用 Ctrl+Insert。
3. **OCR**：使用 Windows 自带的 `Windows.Media.Ocr`，离线、免费。OCR 是**用户框选区域的独立入口**，不是快捷键取词链中自动尝试的一步；M5 实现（D041）。
- 已知限制：目标程序以管理员权限运行而本软件没有时，Windows 会阻止取词。需在帮助文档中说明。

### D012 ✅ 第一版的触发方式：快捷键 + 可选的连按两次 Ctrl+C
- **快捷键**：主要触发方式，默认开启。
- **连按两次 Ctrl+C**：可选，**默认关闭**。
  - 判断依据是剪贴板变化通知（不需要键盘或鼠标监听）。按住 Ctrl 连按两次 C，或松开后再按，均可触发。
  - 间隔小于约 50 ms 的多次剪贴板更新视为同一次复制（有些软件一次复制会写入多种格式）；两次更新间隔在约 50–500 ms 之间才判定为连按。
  - 触发后尝试用 UI Automation 读取上下文，读不到则只翻译选中内容。
  - 价值：远程桌面、虚拟机、管理员权限程序等快捷键取词失败的场景下仍可使用。
- 理由：第一版先把取词的稳定性打磨好；鼠标监听需要在大量软件中反复测试，放进第一版会拖慢发布。

### D013 ✅ 1.1 版本加入"阅读模式"（自动弹出 + 智能小图标）
- 只有开启阅读模式时才启用全局鼠标监听；只用快捷键的用户不产生任何鼠标监听开销。
- **单个英文单词**：双击或拖选后约 300 ms 自动弹出。
  - 在可编辑区域（输入框、编辑器）**不触发**。
  - 300 ms 内用户按键、点击别处或拖动选中内容，则取消弹出。
- **短语或句子**：只显示一个小图标，点击后才翻译；约 2 秒后或鼠标移开时消失；不抢夺焦点。
- 阅读模式下**只用 UI Automation 取词，不模拟 Ctrl+C**；取不到就放弃自动弹出。
- 提供快捷键随时开关阅读模式；支持应用白名单。

### D014 🟡 默认快捷键：要求单手可按，避开常用软件的快捷键
- 要求：**左手单手就能按**（右手握鼠标时不用移动），且不与常用软件冲突。
- 划词翻译的默认快捷键：暂定 **Ctrl+Alt+X**（小指按 Ctrl、拇指按 Alt、无名指按 X，左手不用移动手掌）。
- 截图 OCR、输入翻译的快捷键：在 M1 整理常用软件快捷键清单时一并确定。
- 几乎任何组合都会在某个软件里有冲突（例如 IntelliJ 占用了大量 Ctrl+Alt 组合），因此目标是避开最常用的软件，并提供三层保障：首次启动时由用户确认、可自定义、注册失败时提示更换。
- "连按两次 Ctrl+C"（D012）是另一种单手操作方式。
- 已排除的组合及原因：
  - Alt+D：浏览器的"选中地址栏"。
  - Alt+A：微信截图。Ctrl+Alt+A：QQ 截图。
  - Ctrl+Shift+Z：在 VS Code、Photoshop、浏览器输入框等大量软件中是"重做"。全局快捷键会抢走这个功能。
  - Ctrl+Shift+X：VS Code 的"打开扩展面板"。
- 首次启动时由用户确认或修改；注册失败时提示更换。
- 发布前需整理常用软件的快捷键清单并逐一核对（浏览器、编辑器内部的快捷键无法被系统检测到冲突）。

## 四、词典与 AI

- **补充（2026-10-16，R1-1）**：全局快捷键的字母键按下被系统拦截，前台程序只看到 Ctrl、Alt 按下又松开、中间没有其他键按下（只有字母键的松开）。有的程序把这当成"单独按了一次 Alt"，于是激活菜单栏（手动测试中 VS Code 稳定复现）。处理：快捷键触发时如果 Alt 仍按着，向前台程序补发一次未分配的虚拟键 `0xE8`（与 AutoHotkey 的"菜单屏蔽键"相同），让 Alt 不再是单独按下（`apps/desktop/src-tauri/src/keyboard.rs`）。已用记录键盘事件的测试页（`tools/e2e/key-log.html`）确认程序在 Alt 按下和松开之间收到了这个键。因此默认快捷键仍可使用带 Alt 的组合，选择默认快捷键时不必为此回避 Alt。
- **补充（2026-10-17，R3-P1）：屏蔽键改为"仍按着的修饰键再按一次"**。`0xE8` 虽然没有分配含义，但仍是普通按键：Windows Terminal 收到任何非修饰键都会清除选区，导致 R3-9 取词失败。现在的做法：快捷键触发时 Alt 仍按着，就对快捷键里另一个仍按着的修饰键（优先 Ctrl，其次 Shift，区分左右）补发一次**按下**，不发松开，相当于一次自动重复；用户松开按键时，真实的松开事件照常结束它。Windows Terminal 把 Ctrl、Shift 当修饰键，不清除选区。只有 Alt 加字母、没有其他修饰键时，退回 `0xE8`（这类组合在 Windows Terminal 中仍会清除选区，以后在快捷键设置界面提示）。Shift 也只补发按下：Alt 按着时按一次 Shift 可能切换输入法。
  - **"只按下不松开"的时序问题**：检查"Ctrl 还按着"和补发之间，如果用户恰好松开了 Ctrl，补发的按下会排在真实的松开之后，Ctrl 在逻辑上一直按着。处理：每次补发前在单独的线程上装一个低级键盘钩子（`WH_KEYBOARD_LL`，只存在几毫秒到最多 200 ms，用完即卸载），装好后等 2 ms，让装钩子之前已经过了钩子链、但还没写进按键状态的事件落定，再读按键状态、补发。钩子按系统处理的顺序看到真实事件和我们补发的事件（用 `dwExtraInfo` 标记区分）；如果真实的松开排在补发之前，就再补发一次松开。补发必须由快捷键线程发出，不能由装钩子的线程自己发：一个线程自己 `SendInput` 的事件会插到已排队的真实事件之前送进它自己的钩子，顺序不可信（`tools/e2e/stuck-keys.ps1` 实测：60 次中出现 1 次 Ctrl 卡住，改后 120 次中触发 1 次补发松开、没有卡住）。钩子装不上时退回 `0xE8`。
  - 以后改动快捷键或键盘相关逻辑，必须复测 Windows Terminal 选词，以及 R2-1、R2-2（见手动测试清单开头）。
  - 由项目负责人确认（R3 复测后）。

### D015 ✅ 词典与 AI 相辅相成，各自做擅长的事
| 词典负责（准确、即时） | AI 负责（理解、生成） |
|---|---|
| 音标、词性、基本释义 | 判断当前语境下的含义 |
| 词形还原、考试标签、词频 | 句子翻译 |
| 发音 | 例句、搭配、近义词辨析 |
| — | 解释词典中查不到的词 |
- **把词典释义作为上下文发给 AI**，让 AI 在已有释义中挑选，而不是从零编写。
- 音标、词性一律以词典为准，不由 AI 生成。
- 显示顺序：词典结果毫秒级先显示，AI 结果随后流式补充。
- 词典数据源：**ECDICT**（MIT 协议）。

### D016 ✅ AI 服务商由用户自由选择，可随时更换
- 支持同时配置多个服务商，选择其中一个为默认。
- 可以为不同任务分配不同模型（如查单词用快速便宜的模型，翻译长句用能力更强的模型）。
- 悬浮窗中可一键"换一个模型重新解析"。
- 当前模型超时或出错时，自动切换到备用模型。
- 接口层为适配器结构：先实现 **OpenAI 兼容格式**（覆盖大多数服务商，含 Ollama），Claude、Gemini 等原生接口以后按需增加。
- 内置默认提示词，在高级设置中允许用户编辑。
- 缓存键包含服务商和模型。

### D017 ✅ AI 输出采用分段标记格式，而不是 JSON
- 例如 `【语境】…【例句】…`，客户端边接收边按段落显示。
- 理由：JSON 必须完整接收后才能解析，与流式输出冲突；能力较弱的模型经常写错 JSON 格式。分段标记容错性更好。

### D018 ✅ 默认接入 AI；首次启动引导配置 AI 服务商
- 首次启动的第一步是选择 AI 服务商并填写 API Key（附申请教程链接），并列出 Ollama 本地模型作为选项。
- 可以"跳过"，跳过后词典功能照常可用。
- **不在软件内引导用户申请免费翻译 API**，最多在帮助文档中提及。
- 未来可能由官方提供免费 AI 额度，届时作为一个新的 AI 适配器接入（D007）。

### D019 ✅ 词义按常用程度排序
- **当前语境中的含义永远放在第一位**，高亮显示。
- 其余词义按常用程度排序，显示为"常用 / 较常用 / 少见"三档，**不显示具体百分比**（数据并不精确）。
- **第一阶段（第一版）**：在同一个 AI 请求中顺便完成排序，结果按单词缓存（与语境无关）。
- **第二阶段（1.1 或之后）**：用强模型并参考 WordNet 统计数据，离线生成最常用 2–3 万词的词义频率表，以数据包形式发布（约 1 MB），无 AI 的用户也能看到排序。
- **个人数据叠加**：在用户遇见过的词义旁标注"你见过 N 次"。
- 设置项：**统一排序**（默认，不分词性，每条标注词性）/ **按词性分组**（组内排序）。
- 前置工作：ECDICT 的中文释义需先拆分为独立义项。

### D020 ✅ 不使用 Tatoeba 例句库
- 理由：Tatoeba 的例句未按词义分类，常与当前词义对不上；质量参差不齐；需要额外体积。
- 例句来源：
  - **查词时**：AI 根据当前词义生成例句。
  - **复习时**：优先显示用户自己遇见单词时的原句，其次显示 AI 例句。
- AI 生成的例句随单词一起保存并同步，手机端离线复习时也能看到。

### D021 ✅ 数据包机制，保持安装包轻量
- 安装包只包含**精简版核心词典**（最常用的十几万个词条，去掉用不到的字段）（实际收录规则和数量见 D044）。
- 完整词典、离线翻译模型、词义频率表等做成**可选数据包**，按需下载。
- 数据包独立于软件版本更新。

## 五、生词本与复习

### D022 ✅ 第一版只收藏单词和短语
- 单词表有 `type` 字段（word / phrase），短语动词和固定搭配按"词"收藏。
- 收藏时**自动保存遇见时的原句**和来源（软件名、网址）。
- **查询历史**（自动记录）与**收藏**（用户手动）分开。
- 同一个词查询 3 次以上时，提示"要不要加入生词本？"。
- 句子收藏的数据表先预留，不做界面。

### D023 ✅ 复习算法：FSRS
- 桌面端使用 Rust 实现（rs-fsrs）。
- 手机端 PWA 通过 WebAssembly 使用**同一份** `lextrail-core` 代码，保证各设备计算结果完全一致。

## 六、同步与服务端

### D024 ✅ 数据从第一天起按"可同步"方式设计
- 主键使用 UUID（不用自增 ID）。
- 每条可同步记录都带 `updated_at`、`device_id`、软删除标记 `deleted`。
- **复习日志只追加、不修改**，卡片的 FSRS 状态由日志计算得出，因此多设备离线复习后合并不会冲突。
- 其他数据采用"最后修改者优先"规则。
- 同步数据格式：**操作日志（op-log）**。客户端本地保存完整数据（本地优先），服务器只负责中转。

### D025 ✅ 同步路线：先做自建服务器，以后提供官方托管服务
- 第一阶段：用户自建同步服务器（单文件程序 + SQLite，支持 Docker 一键部署）。
- 以后：官方托管服务使用**同一套服务端代码**，客户端只需修改服务器地址并登录，本地数据会自动重新上传。
- **服务端从第一天起按多用户架构设计**，自建版本默认只开放一个账号：
  - 每张表都有 `user_id`，所有查询按用户隔离；
  - Token 认证（access token + refresh token）；
  - API 带版本号（`/api/v1/`）。

## 十二、性能

### D036 ✅ 路线 A 确认；内存按私有工作集统计（2026-10-15）
- **口径**：性能预算中的内存一律按**私有工作集**（Private Working Set，即任务管理器"内存"列）统计，"总内存"为应用进程及其全部 WebView2 子进程之和。私有提交和工作集只作参考，同时记录在报告中。由项目负责人决定。
- **M0 实测**（`docs/specs/m0-benchmark.md`，`tools/bench`）：纯托盘 1.6 MiB；挂起 15 秒 82.8 MiB，2 小时后系统回收到 13.0 MiB；冷启动显示 288 ms；刚挂起后恢复 11.7 ms；挂起 2 小时后恢复 44.7 ms；空闲 CPU ≈ 0。六项预算全部达标。
- **结论**：按 D008，悬浮窗继续使用路线 A（Tauri / WebView2）；D009 的生命周期设计（挂起而不按时间销毁）得到验证。
- 理由与风险：按私有提交统计约 152–159 MiB，会超出 100 MB；但私有提交包含已换出到磁盘的部分，用户实际看到的是私有工作集。刚挂起时余量只有约 17 MB，而悬浮窗目前还是占位页面，所以 M1、M2、M3、M6 都要重测（见 `ROADMAP.md`）。如果以后不达标，先尝试关闭 GPU 进程、精简页面，仍不行再切换到路线 B。

## 十三、仓库结构与数据

### D037 ✅ 本地数据库放在独立的 `lextrail-store` crate（2026-10-15）
- 新增 `crates/lextrail-store`：桌面端本地 SQLite 的读写、数据库迁移机制都在这里，桌面端只负责调用（D006）。M1 写查询历史时创建。
- `lextrail-core` 只放数据模型和纯逻辑（op-log、合并、FSRS），不依赖 SQLite。
- 理由：`lextrail-core` 要编译成 WebAssembly 给 PWA 用（D029、D030），而 PWA 的本地存储是 IndexedDB；把 SQLite 放进 core 会让 WASM 构建变得困难。存储按 D007 的思路与逻辑分开。由项目负责人同意（M0 架构评审）。

### D038 ✅ 词典预处理工具用 Rust；词典数据不提交到仓库（2026-10-15）
- `tools/dict-builder` 用 Rust 编写，作为 Cargo workspace 成员，crate 名 `lextrail-dict-builder`；与 `lextrail-dict` 共用义项拆分等代码，避免两套逻辑。
- ECDICT 原始数据和生成的精简词典都**不提交到仓库**（也不用 Git LFS）。构建时由 `dict-builder` 下载**固定版本**的 ECDICT，校验 SHA-256 哈希后生成精简词典；CI 缓存下载和生成结果。
- 理由：保持仓库轻量；固定版本 + 哈希保证每次构建结果一致、来源可信。由项目负责人决定（M0 架构评审）。

### D039 ✅ 数据模型公共部分：同步元数据字段、HLC 时间戳、`lookups` 表（2026-10-15）
- M1 开始时按计划评审了 `ARCHITECTURE.md` 第 6 节的公共部分（详细规格见 6.1–6.3），结论如下：
- **同步元数据字段**：`id` 为 UUIDv7 文本（小写、带连字符）；`created_at` 为本机系统时间（Unix 毫秒），只用于显示和排序；`updated_at` 为 HLC 时间戳，"最后修改者优先"只比较它；`device_id`；`deleted`（0/1）。按整行合并。
- **本地表不带 `user_id`**（服务端的表仍按 D025 带 `user_id`）。理由：用户可以先离线使用再登录，本地记录带 `user_id` 会导致登录时改写全部数据。
- **`device_id`** 第一次启动时生成 UUIDv7，存在 `lextrail-store` 的本地 `meta` 表中（不同步），不放在 `settings.toml`。理由：它属于这份数据，只拷贝设置文件不应让两台设备共用一个 ID。
- **HLC 格式**：固定宽度文本 `<12 位十六进制物理毫秒>-<4 位十六进制计数器>-<device_id>`，十六进制统一小写，解析时严格校验，不合格即拒绝。按字符串比较即为先后顺序。理由：SQLite、IndexedDB、JSON 中行为一致；避免 64 位整数在 JS 中超过 2^53 丢失精度；带 `device_id` 保证不同设备的时间戳不相等。
- **HLC 规则**：标准 HLC 算法，放在 `lextrail-core`；计数器溢出时物理部分 +1 ms、计数器归 0；最近一次 HLC 持久化在 `meta` 表，保证系统时间回拨后仍单调递增；必须有单元测试（含溢出、回拨、大写拒绝）。
- **`lookups` 表**：只新增和软删除，不修改；`kind`、`method` 用 CHECK 约束；不保存窗口标题（隐私）；`url` 预留，接入浏览器扩展时再评审隐私处理；同一文字和上下文 30 秒内只记一次，去重逻辑放在 core/store 层；提供"不记录查询历史"开关；AI 相关字段（模型、语境含义）推迟到 M2/M3 设计。
- 已知限制：`lemma` 依赖词典版本，词典更新后以后的统计可能需要重新归一化。
- 推迟的事项（记录在 `ARCHITECTURE.md` 6.5）：M3 确定删除与修改并发时是否"复活"；M4 确定换账号时本地数据的归属、重复 `device_id` 的检测、远端时钟超前的阈值、已删除记录的清理。
- 由项目负责人确认（M1 数据模型评审）。

### D040 ✅ 本地数据库放在 `%LOCALAPPDATA%`，以及它的基本设置（2026-10-15）
- 数据库文件：`%LOCALAPPDATA%\io.github.aspeternity.lextrail\lextrail.db`（Tauri 的 `app_local_data_dir()`），不放在 Roaming（`%APPDATA%`）。理由：域环境下 Roaming 目录会在多台电脑间漫游，导致多台设备共用同一个数据库和 `device_id`，破坏同步（D039）。设置文件仍在 `%APPDATA%`（D035），可以随用户漫游。
- 数据库按需打开：只有功能第一次需要时才打开，只有托盘待机时不打开（D004）。
- 使用 `rusqlite`（`bundled`）；表使用 `STRICT`；连接设置 `journal_mode = WAL`、`synchronous = NORMAL`、`foreign_keys = ON`、`busy_timeout`（5 秒）。
- 迁移用 SQLite 的 `user_version`；每个迁移与版本号更新在同一事务中；遇到版本更高的数据库拒绝打开、不做任何修改（与 D035 中设置文件的处理一致）。
- HLC 时间可注入（`Clock`），测试使用假时钟；`meta` 表中的最近一次 HLC 与数据写入在同一事务中更新。
- 由项目负责人决定（M1 创建 `lextrail-store` 时）。

## 十四、取词与悬浮窗

### D041 ✅ 取词接口：快照 + 后台取词，"取不到"与"出错"分开；UIA 在 MTA 线程上运行（2026-10-15）
- 接口（`ARCHITECTURE.md` 4.1）：`snapshot`（按快捷键时立即调用，只做 Win32 调用，记下前台窗口、进程、类名、标题、权限级别和 `GetGUIThreadInfo` 的 hwndFocus / hwndCaret）→ 检查黑名单（M5）→ `capture`（后台线程）。另有 `capture_context`，供连按两次 Ctrl+C 使用（D012，以后实现）。
- 结果分为 `CaptureOutcome::Unavailable`（取不到：没选中、管理员窗口、没有前台窗口、不支持、超时，悬浮窗给出提示）和 `CaptureError`（出错，写日志）。`CaptureError` 与平台无关（`Platform { operation, code, message }`），Windows 错误在适配器内部转换（D003、D007）。
- 目标是管理员权限窗口（UIPI）时直接返回 `Elevated`，不尝试任何方式；悬浮窗明确提示，并建议改用连按两次 Ctrl+C。目标是 LexTrail 自己时，M1 返回 `Unsupported`。
- 适配器只返回段落或行（`RawContext`，选中位置为 UTF-8 字节偏移、落在字符边界），切句在 `lextrail-core` 中用纯逻辑完成。窗口标题只在内存中使用，不写入数据库。
- UIA 在专用的 COM **MTA** 线程上调用。理由：微软对 UIA 客户端的建议是在不拥有窗口的单独线程上调用，并使用 MTA（https://learn.microsoft.com/windows/win32/winauto/uiauto-threading）。时间预算 180 ms，超时转剪贴板兜底；卡死超过 5 秒的线程放弃并重建，被放弃的线程最多 2 个，超过后暂时停用 UIA。
- OCR 推迟到 M5，作为用户框选区域的独立入口（D011）。
- 由项目负责人确认（M1 取词接口评审）。

### D042 ✅ 悬浮窗焦点：取词期间不抢焦点，取词完成后再获取焦点（2026-10-15）
- 按快捷键后，先记下前台窗口和焦点，再准备悬浮窗；取词期间悬浮窗以不激活方式显示，原窗口保持前台（方案 B）。
- 取词超过约 100 ms 才显示"正在取词"，显示前清空上一次的内容；取词完成后显示结果并获取焦点。
- 取词期间监视前台窗口（`SetWinEventHook(EVENT_SYSTEM_FOREGROUND)`），切换到别的窗口时隐藏并丢弃结果；获取焦点失败时继续监视。
- 钉住状态的焦点规则见 `ARCHITECTURE.md` 9.3。
- 理由：悬浮窗一出现就抢焦点，会让 UIA 拿错焦点元素，剪贴板兜底也无法向原窗口发送 Ctrl+C；先取词再显示则每次都要多等最多约 200 ms。
- 已否决：方案 A（先取词，再显示并获取焦点）。
- 由项目负责人选择（M1 取词接口评审）。
- **补充（2026-10-17，R3-P4）："正在取词"的计时不含按住快捷键的时间**。剪贴板兜底要等快捷键松开才复制（D043），正常按一下也要等约 150–200 ms，于是每次都闪一下"正在取词…"。现在取词过程会报告"在等松开快捷键"和"已松开"；约 100 ms 的计时在松开时重新开始，所以松手后复制很快完成时直接显示结果。按住超过约 1 秒时显示"松开快捷键后取词…"，超过约 3 秒显示"请松开快捷键后再试"（D043 补充）。由项目负责人确认。
- **补充（2026-10-17，R3-P3）：取词线程先于创建悬浮窗启动**。第一次查词时创建悬浮窗会在快捷键线程上同步阻塞一段时间；原来取词线程在这之后才启动，并没有与创建窗口并行。现在顺序为：屏蔽键 → 记录前台窗口 → 启动取词线程 → 请求显示悬浮窗（可能创建窗口）。

### D043 ✅ 剪贴板兜底：何时运行、发什么键、如何恢复剪贴板（2026-10-17）
- **何时运行**：UIA 返回"不支持"、超时或出错时，剪贴板兜底照常接着尝试（D011）。UIA 返回"没有选中文字"时，**只对 UIA 不可靠的程序**再用剪贴板确认一次：目前是 Chromium 系窗口（类名 `Chrome_WidgetWin_*`：Chrome、Edge、VS Code 等 Electron 程序）。记事本、Word、Windows Terminal 等 UIA 可靠的程序不确认，避免多余的延迟（约 400 ms）和剪贴板操作。理由：手动测试 R1-3、R1-4 中，VS Code 编辑器、集成终端和刚打开的 Chrome PDF 已经选中却被 UIA 报告为"没有选中"；而可靠程序的"没有选中"是真的。由项目负责人确定（第二阶段计划）。
- **发什么键**：一般程序发 Ctrl+C；终端发 Ctrl+Insert（Windows Terminal、conhost、mintty、ConEmu，以及焦点在 VS Code 集成终端 `xterm-helper-textarea` 上时），因为终端里没有选区时 Ctrl+C 会中断正在运行的程序。2026-10-17 实测：Windows Terminal、conhost、VS Code 终端的 Ctrl+Insert 都能复制选区；没有选区时什么都不发生（VS Code 终端中运行的 `ping -t` 未被中断）。
- **"复制了但不是选区"**：VS Code 编辑器在没有选区时按 Ctrl+C 会复制整行，同时在 Chromium 的 `Chromium Web Custom MIME Data Format` 中写入 `vscode-editor-data`，其中 `"isFromEmptySelection":true`；据此判定为"没有选中文字"。
- **剪贴板没有变化**（序列号 400 ms 内未变）：判定为"没有选中文字"，不改动剪贴板。
- **保存与恢复**：复制前保存剪贴板中所有"内存类"格式（文本、HTML、RTF、`CF_DIB`、文件列表 `CF_HDROP`、各程序注册的自定义格式等）；GDI 句柄类格式（`CF_BITMAP`、`CF_ENHMETAFILE`、`CF_METAFILEPICT`、`CF_PALETTE` 等）不保存，它们大多由系统从内存类格式自动合成（如 `CF_BITMAP` 由 `CF_DIB` 合成）。总大小超过 64 MB、或当前剪贴板所有者无响应（读取延迟渲染的格式会卡住）时，不使用剪贴板兜底（返回"不支持"），不碰用户的剪贴板。读取后立即写回保存的内容，并附加 `ExcludeClipboardContentFromMonitorProcessing`、`CanIncludeInClipboardHistory = 0`、`CanUploadToCloudClipboard = 0`，使写回不进入剪贴板历史和云剪贴板。
- 已知限制：目标程序自己的复制会在剪贴板历史（Win+V）中留下一条记录，无法避免；写回会触发其他剪贴板监视程序的变化通知（多数监视程序会遵守上述排除标记）；只保存内存类格式，个别程序只放 GDI 句柄类格式时，恢复后可能缺少这种格式。
- 剪贴板兜底只返回选中的文字，没有上下文（悬浮窗不显示句子）。
- **补充（2026-10-16，R3-P2）：等待松开修饰键**。剪贴板兜底一直等到快捷键的修饰键全部松开再发复制键（否则 Ctrl+C 会变成 Ctrl+Alt+C）；兜底时间约 3 秒（原为 600 ms）。超过兜底时间仍按着时，不复制、不碰剪贴板，悬浮窗提示"请松开快捷键后再试"（不再显示"取词超时 / 程序响应较慢"，那是原因不对的提示）。理由：R3 中按住 Ctrl+Alt 超过约 0.6 秒就会超时，而走 UIA 的程序按住也能正常取词，两条路径的表现应当一致。由项目负责人确定。
- **补充（2026-10-20，R4-P2）：确认没有完成时不采用未经确认的"没有选中"**。UIA 报"没有选中"、剪贴板步骤作为确认运行时：确认步骤没能完成检查（按着键 `KeysHeld`、超时 `TimedOut`、出错）→ 采用确认步骤的结果（如"请松开快捷键后再试"），因为用户很可能确实选了文字；确认步骤主动不运行（`Unsupported`：剪贴板超过 64 MB、所有者无响应）→ 仍报"没有选中文字"，因为报"不支持"会让人以为整个程序不能取词，而 UIA 的结果是仅有的信息。不作为确认的普通回退仍按原优先级。由项目负责人提出（`KeysHeld`）；`TimedOut`、出错、`Unsupported` 的取舍由 AI 提出，项目负责人同意（2026-10-20）。R4-12 复测通过。

## 十五、词典

### D044 ✅ 精简词典：ECDICT 固定提交、收录规则 B+、义项拆分规则（2026-10-20）
- **数据来源**：ECDICT 仓库中的 `ecdict.csv`，固定在提交 `82c9872`（2025-01-02，该文件最后一次修改），按大小和 SHA-256 校验（D038）。不用 GitHub Release 的数据包：最新 Release 是 2017 年的，之后的修正只在仓库里。
- **收录规则 B+**（约 27.8 万词条，生成文件 33.4 MiB）：有中文释义，且满足其一：有词频 / 考试标签 / 柯林斯 / 牛津标记；是带音标的单词；是释义不以领域标记开头的短语（如 give up、in terms of）。理由：只收有标记的词（约 5.9 万）会查不到很多学术和技术词；全收（约 77 万）大多是专业术语和专业短语，文件约大一倍。
- **义项拆分**：按词性行拆；行内有分号时只按分号拆（逗号是同一义项内的近义说法）；整行没有分号时按逗号拆；括号内和数字间的逗号不拆。理由：ECDICT 老词条全部用逗号分隔不同义项（如 real 的"真的, …, 实数的"），只按分号拆会让常用词每个词性只有一个很长的义项，D019 的义项排序就没有意义。这修正了 `ARCHITECTURE.md` 5.2 原来"逗号分隔的属于同一义项"的说法。
- **音标**：西里尔字母 `ә` 统一替换为 IPA 的 `ə`，其余原样保留；ECDICT 只有一个音标，不分英美。
- 格式与细则见 `docs/specs/m1-dict.md`。由项目负责人决定（2026-10-20）。
- **补充（2026-10-20）：变形词条与原形词条**。查到的词本身有释义、同时是另一个词的变形时（better、left、found），两个词条都给，变形在前、原形在后，但变形词条必须标出和原形的关系，如"left（leave 的过去式）""better（good 的比较级）"；变形词条只是"xx 的过去式"之类说明时只给原形。按语境排序留到 M2（D019）。由项目负责人决定。
- **补充（2026-10-20）：带连字符的复合词**。整体查不到时按 `-` 拆开查各部分，结果标明"词典没有整词，以下是各部分的释义"；跳过虚词（to、of、and 等），不显示它们的词条。查询接口区分"整词查到"（`lookup`）和"拆开查到"（`lookup_with_parts`）；合并行末连字符（`resolve_line_end_hyphens`）只能用整词查询判断，不能因为拆开查到就合并（English-to-German 保持原样，compu-tation 仍合并）。由项目负责人决定。
- **补充（2026-10-20）：收录规则不放宽，保持 B+**。评估过"单个单词、有中文释义、释义不以领域标记开头即收录"：多 96,888 条、9.8 MiB；第 9 节的普通词汇缺口只补上 parallelization、overfitting（convolutional、optimizer、subword 的释义以领域标记开头，仍收不到）；抽样 50 条中 36% 是错误、过时或价值很低的词条。专业词交给 D021 的完整词典数据包和 M2 的 AI。数据见 `m1-dict.md` 10.1。由项目负责人决定。
- **补充（2026-10-20）：行末连字符用完整版词头表判断（方案 A）**。额外存一份"完整版 ECDICT 有、精简版没有"的纯字母单词词头（约 16.5 万个、2.2 MiB），只用于判断行末连字符是否合并（如 convolu-tional），释义仍只查精简词典；判断时词头表也走后缀规则（合并后是复数、过去式等）。不采用"任一片段不是单词就合并"（方案 B），因为它会把 LSTM-based、COVID-related 等真复合词误合并成不存在的词；方案 A 出错时只是保留连字符。数据见 `m1-dict.md` 10.2。由项目负责人决定。

### D045 ✅ 输入分类：单词 / 短语 / 句子（2026-10-20）
- 选中的文字不含任何英文字母（纯中文、数字、符号）时，不查词典、不请求 AI、不写查询历史，悬浮窗提示"目前只支持英文"。
- 规范化后只有一个词 → 单词（含带连字符的复合词）。
- 多个词：整体在词典里 → 短语；否则不超过 5 个词、且不以句末标点（`.` `!` `?` `…` 及中文句末标点）结尾 → 短语；其余 → 句子。
- 理由：短语走"词典 + AI 语境解析"，句子走"AI 翻译"；两三个词到五个词的术语（`multi-head attention`）按短语解释比按句子翻译更有用，而带句末标点或更长的文字通常是句子。上限 5 由项目负责人选定（另一选项是 3，或只有词典里有的才算短语）。
- 细则见 `docs/specs/m1-dict.md` 第 11 节。由项目负责人决定（2026-10-20）。
