# M1 连按两次 Ctrl+C

> 状态：**草稿**（2026-10-21，分支 `feat/double-copy`）。第一阶段（本文 + 连按判定逻辑和单元测试）、第二阶段（Windows 剪贴板监听、`capture_context`、桌面端接入）已完成，第二阶段的实机测试（模拟按键、Excel）还没跑；第三阶段（e2e、文档）未做。相关决定：D011、D012（及其补充）、D042、D043。标"由项目负责人确定"的是 AI 提出、项目负责人 2026-10-21 确认的。

## 一、开关

- **默认关闭**（D012）。设置文件 `settings.toml`（位置由项目负责人确定）：

  ```toml
  [hotkeys]
  double_ctrl_c = false
  ```

  和 `[history] record` 一样先只放在设置文件里；界面开关随快捷键设置界面一起做（ROADMAP）。放在 `[hotkeys]` 下，是因为它是另一种触发方式（D014："连按两次 Ctrl+C 是另一种单手操作方式"），界面上也和快捷键放在一起。
- 关闭时不注册剪贴板监听，没有任何开销。
- 和其他设置一样，**启动时读一次**，改设置后重启生效（项目负责人确定）。

## 二、判定规则

实现在 `lextrail-capture` 的 `double_copy.rs`（`DoubleCopyDetector`，与平台无关，单元测试覆盖下面每一条）。平台侧只负责收到剪贴板更新通知、读出内容、记下收到通知的时间，交给它判断。

1. **同一次复制**：两次剪贴板更新相隔不到 **50 ms** 算同一次复制（有些程序一次复制会写几次剪贴板，D012）。这次复制的内容以最后一次更新读到的为准。
2. **连按**：一次复制的最后一次更新与下一次复制的第一次更新相隔 **50–500 ms**（含两端），算连按（D012）。
3. **两次必须是相同的文字**（D012 补充，项目负责人提出）：第二次复制必须是文字，并且和第一次的文字完全相同（区分大小写，不做任何规范化）。对同一个选区按两次 Ctrl+C 得到的文字一定相同，所以没有代价；一次复制写两次不同内容的程序、复制图片 / 文件都不会触发。只有空白字符的文字不触发。
4. **触发一次之后**：组成连按的第二次复制不能再和第三次组成连按，第三次重新开始算（按三下只触发一次；按四下触发两次）。
5. **VS Code 没有选区时的整行复制**（D043，`isFromEmptySelection`）：复用 `clipboard_rules::is_vscode_empty_selection_copy` 识别。两次都是这种整行复制、并且内容相同时，算连按、结果是**"没有选中文字"**（悬浮窗显示和快捷键查词一样的提示），**不去查整行**。一次整行复制、一次真正的选区复制，不算连按。
6. **自己的剪贴板兜底产生的更新一律忽略**：快捷键查词走剪贴板兜底时，会有两次剪贴板更新（模拟复制、写回原内容），两次常隔 50–500 ms，绝不能算连按。做法：**从按下快捷键（开始取词）起，到正在进行的取词全部结束（剪贴板已写回）之后再等 300 ms**，这段时间内的剪贴板更新都忽略；而且这段时间之前的一次复制不能和之后的一次组成连按。
   - 按查词编号记（项目负责人审阅时指出）：快速连按两次快捷键时两次取词会重叠（R1-5），只记一次的话，第一次结束就会提前结束第二次的忽略期。所以每次取词带自己的编号开始和结束，**最后一个结束后**再等 300 ms。
   - 某次取词万一没有报告结束，从它开始起 10 秒后不再算它。
   - 写回原内容时本来就带了 `ExcludeClipboardContentFromMonitorProcessing` 标记（D043），第二阶段的监听也会按下一条忽略它；时间窗口是另一层保险，覆盖模拟复制那一次（那次是目标程序自己写的，没有标记）。
7. **带"不要监视"标记的更新忽略**（由项目负责人确定）：剪贴板里有下面任一标记时，不读文字、不算任何一次复制，并清掉之前的一次复制：
   - 有 `ExcludeClipboardContentFromMonitorProcessing` 格式（密码管理器复制密码时会加这个标记，我们自己写回时也加）；
   - 有 `CanIncludeInClipboardHistory` 格式且值（DWORD）为 0（"不要进剪贴板历史"；有的程序复制密码时只加这一个标记）。值为 1 或没有这个格式时照常处理。

   理由：用户在密码管理器里连按两次复制密码时，不应该把密码拿去查词、写进查询历史。
8. **LexTrail 自己的窗口在前台时忽略**（由项目负责人确定）：悬浮窗或主窗口在前台时的剪贴板更新不算复制，不触发查词。

## 三、触发之后

1. 记录当时的前台窗口（`TextCapture::snapshot`，和快捷键一样）。
2. 用 UIA 读选中文字所在的上下文（`TextCapture::capture_context(target, text)`）：取焦点元素的选区和它所在的段落 / 行（和快捷键取词的 UIA 步骤用同一套查找方法）；读不到（不支持 UIA、程序以管理员权限运行、选区已被清掉、超时等）就**只查选中的文字，不显示原句**（D012）。不再模拟任何按键，不再碰剪贴板。
   - **以剪贴板里的文字为准**（项目负责人确定）：UIA 读到的选区文字必须和剪贴板文字"对得上"才用它的上下文——按空白切分后的词完全相同（只忽略空白和换行的差别，如复制时换行变成 `\r\n`；区分大小写）。对不上时只查剪贴板文字、不显示原句，**不会换成 UIA 读到的文字**（日志里记 `context_mismatch`）。
   - **跑在 UIA 专用线程上**，和快捷键取词共用同一个工作线程，超时也一样（180 ms，第一次多给 500 ms 启动时间；Chromium 窗口第一次取词时在预算内重试）。上一个 UIA 请求还没完成时直接放弃上下文。
   - Edge 的 PDF 阅读器不读上下文（UIA 报告的选区会错位，D041），但会像剪贴板兜底一样合并行末断开的单词。
3. 查词、显示悬浮窗、获取焦点的方式与快捷键查词相同（D042、D046）。
4. 查询历史里 `method` 记为 **`clipboard_double_copy`**（`lextrail_core::lookup::CaptureMethod::ClipboardDoubleCopy`，数据模型里已有）。
5. 管理员权限运行的程序：程序自己写剪贴板，所以连按仍能触发（这是 D012 说的价值之一），只是读不到上下文。

## 四、终端里的情况（实测，2026-10-21）

Windows Terminal 和 VS Code 终端里，**有选区时 Ctrl+C 复制并清除选区；没有选区时 Ctrl+C 发给正在运行的程序（中断它）**。所以在终端里连按两次 Ctrl+C：

- 第一次：复制选区，选区消失，程序继续运行；
- 第二次：已经没有选区，Ctrl+C 中断正在运行的程序，**剪贴板没有第二次更新**。

结果是：**终端里连按两次 Ctrl+C 永远不会触发查词，而且会中断正在运行的程序。** 在终端里查词请用快捷键（剪贴板兜底在终端里用 Ctrl+Insert，不会中断程序，D043）。

测试方法：单独开一个 Windows Terminal 窗口（`wt -w new`，运行 `cmd /k ping -t 127.0.0.1`），以及一个单独的 VS Code 实例（临时用户目录，打开文件夹时自动运行任务 `ping -t 127.0.0.1`，任务终端和集成终端一样是 xterm.js）；用真实鼠标拖选一行输出，模拟按两次 Ctrl+C（中间松开 Ctrl / 按住 Ctrl 两种，间隔 200 ms）。发键前确认前台是测试窗口，截图只截测试窗口，测试前后保存并恢复剪贴板文字。按 ping 的进程号判断是否被中断，并截图核对：

| 终端 | 按一次 Ctrl+C（有选区） | 再按一次（200 ms 后） |
|---|---|---|
| Windows Terminal | 剪贴板更新，选区消失，ping 2.5 s、6.5 s 后仍在运行 | 剪贴板**没有**更新；ping 被中断（`Control-C`） |
| VS Code 终端（任务终端） | 剪贴板更新，选区消失，ping 仍在运行 | 剪贴板**没有**更新；ping 被中断（"terminated with exit code: 1"） |

中间松开 Ctrl 和一直按住 Ctrl 结果相同。conhost（旧控制台窗口）和 VS Code 普通集成终端没有单独测；VS Code 两者都是 xterm.js、复制的快捷键规则相同。

**设置项说明（草稿，以后放进设置界面）**：

> 连按两次 Ctrl+C 查词（默认关闭）
> 在任意程序中选中英文，快速按两次 Ctrl+C 即可查词，适合快捷键无法取词的场合（远程桌面、虚拟机、以管理员身份运行的程序）。
> 注意：在终端（Windows Terminal、命令提示符、VS Code 终端等）中，第一次 Ctrl+C 会复制并清除选区，第二次会中断正在运行的程序，因此终端里请用快捷键查词。

## 五、读剪贴板的要求（由项目负责人确定）

Excel 等程序复制大片内容时是**延迟生成**的（delayed rendering）：复制时只登记格式，有人读某种格式时才当场生成。监听程序一读 `CF_UNICODETEXT`，就会逼它当场生成全部文字。Windows 自己的剪贴板历史（Win+V）也是这样读的，所以可以接受，但要做到：

1. **打开的时间尽量短**：`OpenClipboard` 之后只做必要的事——先查标记格式（第二节第七条，查到就不读文字），再读文字和 VS Code 的整行标记，复制到自己的内存后马上 `CloseClipboard`；判定、日志等都在关闭之后做。
2. **打不开时短暂重试，不卡住监听线程**：别的程序正打开着剪贴板时 `OpenClipboard` 会失败。重试几次、每次间隔很短（总共不超过约 100 ms），仍打不开就把这次更新当作"读不到"（`CopiedContent::Other`）。监听线程不能长时间阻塞，否则后续的更新通知会排队。
3. **先判断再读**：开关关闭时不注册监听（第一节）；LexTrail 自己的窗口在前台、或处在自己取词的忽略期内时，不打开剪贴板（第二节第六、八条），避免无谓地逼别的程序生成内容。
4. 第二阶段测试：用 Excel（项目负责人电脑上装了的话）复制一大片单元格，确认 Excel 和 LexTrail 都不会明显卡顿，并记下读剪贴板用的时间。
